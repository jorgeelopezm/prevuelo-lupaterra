## Context

`/aeronave` (`fleet` module, `src/modules/fleet/index.ts`) is one of the four screens still calling `registerPlaceholderScreen`. Everything it needs already exists: the module registration contract (`src/modules/types.ts`, `registry.ts`), the locale-scoped path segments derived from the catalogs (`src/platform/i18n/segments.ts`), the fragment/full-page renderer honoring `HX-Request` (`src/server/views/views.ts`), the shared design-system partials (`src/views/partials/components.njk`), the session/CSRF/ownership primitives (`src/platform/identity/`), and the pooled, migration-managed PostgreSQL layer (`src/platform/db/`). `meteorologia-page` has already walked this path once for a read-only screen fed by an external service.

What is new here is that this is the **first write-heavy, pilot-owned domain** in the application. Every prior feature table (`pilots`, `sessions`, `documents`, `document_chunks`) was either identity or reference data; `data-foundation` explicitly deferred feature-domain tables to the capability that needs them, and this is that capability. So this change has to establish the patterns the checklists and risk modules will copy: how a pilot-owned aggregate is scoped, how forms are validated and posted without JavaScript, how derived figures are computed rather than stored, and how a file upload enters the system.

It is also the first screen with a genuine tension against the standing provenance rule. The prototype's `Aircraft` screen (`diseno/src/App.tsx`, screen 5) shows an engine strip with CHT/EGT/oil values, a maintenance schedule with due dates and Hobbs readings, and Hobbs/tach/fuel tiles — all sample constants. Every one of those is exactly the kind of "operational-looking data without provenance" the repository forbids. The resolution taken here is not to drop the panels but to give each one a real source: maintenance and documents are pilot-entered records (provenance = the pilot, stated as such), and engine values exist only when the pilot has imported an actual avionics data file.

Constraints inherited and not renegotiated here: server-rendered Nunjucks with htmx fragments, no SPA and no client router; Spanish/Portuguese/English from the catalogs with no hardcoded UI strings; forward-only migrations with uuid PKs, UTC timestamps, the `set_updated_at` trigger, and a non-nullable `pilot_id`; ownership violations answered 404, never 403; mobile-first from 320px with 44px touch targets; `npm run check` green.

## Goals / Non-Goals

**Goals:**

- Make `/aeronave` the pilot's system of record for aircraft identity, airworthiness validity, weight and balance reference data, flights flown, maintenance due conditions, and imported engine recordings.
- Establish the pilot-owned-aggregate pattern (schema shape, ownership scoping, form handling, derived figures) that checklists and risk will reuse.
- Keep every displayed figure either directly entered by the pilot or derived at render time from entries the pilot made — nothing stored as a hand-editable total, nothing displayed without a source.
- Make the active-aircraft designation a first-class, cross-module fact readable from the shell and by later modules.
- Work entirely without JavaScript for create/read/update/delete, with htmx used only to make panel updates feel immediate.

**Non-Goals:**

- Computing weight and balance, drawing the CG envelope, or producing a loading sheet. The profile is captured here so the calculation can live where the go/no-go decision does.
- Charting engine data over time across flights, trend analysis, or exceedance detection beyond drawing a pilot-entered limit line on the most recent flight.
- Any maintenance workflow beyond the pilot's own reminder list — no work orders, no CRS signatures, no organisation roles, no claim that the record is the aircraft's official continuing-airworthiness record.
- Multi-pilot or club fleets: an aircraft belongs to exactly one pilot in this change.
- Importing a logbook from another application, or exporting a printable FCL.050 logbook. Both are natural follow-ups; neither is needed to make the screen useful.
- Deriving *legal currency* verdicts. Recent-experience figures are counted and shown; the app never says a pilot is or is not current.

## Decisions

**1. One `flight_entries` table covering both aircraft legs and FSTD sessions, discriminated by a `kind` column.**
A flight and a simulator session share most of the FCL.050 columns (date, function times, night, IFR, remarks) and belong in one chronological listing. `kind` is `'flight' | 'fstd'`; `aircraft_id` is non-null for `'flight'` and null for `'fstd'`, with `device_type`/`device_qualification` the mirror image, both enforced by table check constraints. *Alternative considered:* two tables, joined or unioned for the listing. Rejected — it duplicates a dozen shared columns and forces a `UNION` in every totals query, for a distinction that is one boolean in practice. The spec's requirement that FSTD time never touch an aircraft total is then a `WHERE kind = 'flight'` in the aircraft aggregates, which is easy to test directly.

**2. Durations stored as integer minutes; counter readings stored as `numeric`, never floating point.**
`total_minutes`, `night_minutes`, `ifr_minutes`, `pic_minutes`, and the rest are `integer`. Hobbs and tach readings, which are decimal hours by instrument convention, are `numeric(10,2)`; weights and arms are `numeric` with an explicit scale. *Alternative considered:* decimal hours (`numeric(5,1)`) for durations, matching how pilots write them. Rejected — every derived total is a sum over potentially thousands of rows, and integer minutes make the sums exact and the "0.9 + 0.9 + 0.6" rounding question disappear. The form still accepts and redisplays decimal hours or `h:mm`; conversion happens once at the parse boundary, and the display formatter is the inverse. Floating point (`real`/`double precision`) is excluded everywhere.

**3. Flight date is a calendar `date`; departure and arrival times are UTC `time` values; there is no `timestamptz` for the flight itself.**
FCL.050 records a calendar date plus UTC clock times, and the application does not know the aircraft's local timezone. Storing a `timestamptz` would require inventing one. The `created_at`/`updated_at` audit columns remain `timestamptz` per the data-foundation convention. A flight that crosses midnight UTC is handled by taking `total_minutes` as authoritative rather than recomputing it from the two clock times — the times are a record, the duration is the datum.

**4. All totals are computed in SQL at render time; nothing is materialized.**
Aircraft airframe/engine/tach hours and landing counts come from `SUM`/`COUNT` over that aircraft's `kind = 'flight'` entries plus the aircraft's `opening_*` offset columns; pilot totals and the 90-day recency windows come from the same table filtered by `pilot_id` and a date predicate. *Alternatives considered:* (a) counter columns updated on write — rejected outright, the specs forbid a stored total and counters drift the moment an entry is edited or deleted; (b) a materialized view refreshed on write — rejected as premature: a GA pilot's lifetime logbook is in the low thousands of rows, and an index on `(pilot_id, aircraft_id, flight_date DESC)` makes these aggregates trivial. Revisit only with a measurement.

**5. `pilots.active_aircraft_id uuid NULL REFERENCES aircraft(id) ON DELETE SET NULL`, plus a retirement guard in the application.**
The designation is a single scalar owned by the pilot, so it lives on the pilot row rather than in a preferences table we do not otherwise need. Deleting the aircraft nulls it; *retiring* an aircraft is an application-level state change, so the fleet service clears the designation in the same transaction as the retirement. This creates a mutual reference between `pilots` and `aircraft` — resolved by creating `aircraft` in migration 004 and adding the column to `pilots` with `ALTER TABLE` in the same migration, after the table exists. *Alternative considered:* a `pilot_preferences` table. Rejected as a table with one meaningful column; it can be introduced later without changing the read path if preferences multiply.

**6. Child tables carry a redundant `pilot_id` and are keyed against a composite unique on the parent, so ownership is one predicate everywhere.**
`aircraft_documents`, `aircraft_load_stations`, `maintenance_items`, `flight_entries`, and `engine_data_files` each carry `pilot_id uuid NOT NULL REFERENCES pilots(id) ON DELETE CASCADE` alongside their `aircraft_id`/`flight_entry_id`. `aircraft` gains `UNIQUE (id, pilot_id)` and children declare `FOREIGN KEY (aircraft_id, pilot_id) REFERENCES aircraft (id, pilot_id) ON DELETE CASCADE`, so the database itself makes a cross-pilot mismatch unrepresentable. *Alternative considered:* deriving ownership by joining up to `aircraft` in every query. Rejected — it makes the scoping predicate structural rather than uniform, and one forgotten join is a data-leak bug. The redundancy is denormalization bought deliberately, and the composite FK removes the usual objection that it can go out of sync.

**7. Per-pilot registration uniqueness is a functional unique index on a normalized form.**
`CREATE UNIQUE INDEX aircraft_pilot_registration_uniq ON aircraft (pilot_id, upper(regexp_replace(registration, '[^A-Za-z0-9]', '', 'g'))) WHERE retired_at IS NULL` — so `EC-ABC`, `ec abc`, and `ECABC` collide for one pilot, never across pilots, and a retired aircraft does not block re-registering the same tail. The display value stores exactly what the pilot typed.

**8. Engine samples are stored as one compact JSONB series per imported file, not as sample rows. (This supersedes the indicative `engine_data_samples` table named in the proposal.)**
`engine_data_files` holds the provenance columns (filename, byte size, sha-256 digest, detected format, imported-at, `pilot_id`, `flight_entry_id`) plus `channels jsonb` (the recognized channel descriptors with their units) and `series jsonb` (a column-oriented `{ t: [...], values: { cht1: [...], … } }` document, downsampled at import to a bounded number of points), plus `ignored_columns text[]`. A one-hour flight logged at 1 Hz across twelve channels is ~43,000 sample rows and one JSONB document; the screen only ever renders a strip of per-channel min/max/last over the whole flight. *Alternatives considered:* (a) a normalized `engine_data_samples` table — rejected on row volume for a read pattern that never queries an individual sample; (b) keeping the raw file on disk or in object storage — rejected because no blob store is configured, and JSONB keeps the import atomic with the rest of the transaction. The raw file is not retained after parsing; its digest and metadata are, which is what the provenance requirement actually asks for. If per-sample querying is ever needed, the normalized table can be added alongside without changing the display path.

**9. Engine-monitor formats live behind a small registry with `detect(headers)` and `mapChannels(headers)`, and the CSV parser is written in-repo.**
`src/modules/fleet/engine-data/formats/` holds one module per supported export (JPI EDM-class, Garmin-class, Dynon-class, plus a generic header-name matcher as the fallback), each exporting a detector and a channel map; the importer picks the first detector that matches and reports the format it used. The CSV reading itself is ~60 lines handling quoted fields and CRLF — smaller than the surface of adding and pinning a parser dependency, and the repository's dependency list is deliberately short. *Alternative considered:* `papaparse` or `csv-parse`. Rejected on that dependency-weight ground; revisit if a format needs real dialect handling.

**10. `@fastify/multipart` is the one new runtime dependency, configured with a hard byte limit, a single-file limit, and a text/csv content-type check.**
`@fastify/formbody` is already registered and handles every other form on the screen; the engine-data upload is the only multipart route. Limits come from configuration (`ENGINE_DATA_MAX_BYTES`, default 8 MiB) so the oversized-file rejection in the spec is a real, tunable boundary rather than a hardcoded number. *Alternative considered:* a paste-the-CSV textarea, avoiding the dependency. Rejected — engine exports are megabytes and pasting them is not a usable flow.

**11. All mutations are plain `POST` + redirect (Post/Redirect/Get) carrying the existing CSRF token; htmx enhances but is never required.**
Each form posts to a localized action path and, on success, redirects back to the screen with the affected aircraft selected; on validation failure the handler re-renders the same partial with field-level messages and the submitted values preserved, status 422. htmx is layered on by targeting the individual panel partial, so the same handler serves both presentations exactly as `ViewRenderer` already arranges — no second code path. This satisfies the "navigation without JavaScript" requirement for a write-heavy screen and reuses `src/platform/identity/csrf.ts` unchanged.

**12. Sub-paths are localized from the catalogs, like the top-level segments.**
The module resolves its own sub-segments (`aircraft`, `logbook`, `maintenance`, `documents`, `engine-data`, `new`, `edit`, `delete`) through `fleet.segment.<name>` catalog keys, with a `fleetPath(sub, locale, params)` helper layered over `destinationPath('fleet', locale)`. *Alternative considered:* a single base path with an `action` form field. Rejected — it makes every sub-view unbookmarkable and collapses six distinct handlers into one dispatcher, and the catalogs already own segment localization for the top level, so following that convention costs a few keys.

**13. Validation is `zod` at the form boundary, following `src/modules/weather/query.ts`.**
One schema per form, parsing the URL-encoded body into a typed command object, with the error map producing catalog keys rather than English messages so the field-level messages localize. Cross-field rules from the specs (night ≤ total, sum of function times ≤ total, in ≥ out, empty weight ≤ MTOW, expiry ≥ issue) are `superRefine` checks on the same schema, so the route handler has one failure path.

**14. Layout: a single stacked column of panels at phone width, two columns at `lg`, with the aircraft selector as a horizontally scrollable chip row.**
Panels in order: aircraft identity, airworthiness/documents, derived totals tiles, maintenance, engine trend, logbook listing. Each panel is its own partial and its own htmx target. This reuses the existing `card`, `badge`, and `emptyState` partials and the shell's existing breakpoints; no new layout primitive and no new CSS framework. The prototype's three-across totals tiles become a single column at 320px and only regain their row at `md`.

**15. Advance-warning windows are configuration, not constants.**
`DOCUMENT_WARNING_DAYS` (default 30), `MAINTENANCE_WARNING_DAYS` (default 30), and `MAINTENANCE_WARNING_HOURS` (default 10) join the shared Zod config schema. The specs deliberately say "the configured advance-warning window" so the threshold is testable and adjustable without touching view code.

**16. Seed data is labeled sample data and lives behind the existing production guard.**
The development seed gains one aircraft, a handful of flights, two documents, and two maintenance items for the existing seeded pilot, each carrying the sample-data marker the seed already uses, so the screen can be exercised locally without inventing values in templates. No engine-data file is seeded — the no-data-imported state is the one the seed should show.

## Risks / Trade-offs

- **[Risk] The engine panel is the single largest fabrication hazard in the repository: a template default, a chart library placeholder, or a seeded example would put unsourced CHT/EGT values on screen and violate the Tier 1 rule.** → Mitigation: an eval test renders the screen for an aircraft with flights but no import and asserts the response body matches no numeric-plus-unit pattern for any engine channel (`°C`, `°F`, `PSI`, `RPM`, `GPH`, `V`), and separately asserts none of the prototype's engine constants appear anywhere in the repository's templates. The strip renders from a partial that takes the series as a required parameter, so there is no code path that draws it with no data.
- **[Risk] The proposal's four capabilities land as one screen, so the change is large and the temptation is to ship a half-wired page.** → Mitigation: the task breakdown sequences them so each capability is independently complete and testable — aircraft records and the active designation first (the screen is useful with only that), then the logbook and derived totals, then maintenance, then engine import last as the only genuinely optional slice. If the change has to be cut, it is cut at a capability boundary.
- **[Risk] `feature-scaffolding`'s "placeholder screens" requirement is being modified concurrently by the unarchived `meteorologia-page` change; whichever archives second overwrites the other's version of that requirement block.** → Mitigation: this change's `MODIFIED` block is written to carry *both* exclusions and both scenarios, so archiving it after `meteorologia-page` is correct. If it archives first, `meteorologia-page`'s narrower block must be updated to keep the aircraft exclusion before it is archived — called out as a task.
- **[Risk] Denormalized `pilot_id` on every child table can drift from the parent's owner.** → Mitigation: the composite `(id, pilot_id)` foreign keys (decision 6) make drift a constraint violation rather than a silent inconsistency; a schema test asserts every new pilot-owned table declares both the `pilot_id` column and the composite reference.
- **[Risk] Derived totals recomputed on every render become slow for a pilot with a decade of entries, and the 90-day recency window is a second pass over the same table.** → Mitigation: one query returning both the lifetime aggregates and the windowed counts via `FILTER` clauses, backed by `(pilot_id, flight_date DESC)` and `(aircraft_id, flight_date DESC)` indexes; measured against a seeded 5,000-entry logbook in the verification step. The stored-counter escape hatch stays available and is explicitly not taken now.
- **[Trade-off] Not converting units means a pilot who enters an aircraft in pounds/inches and another in kilograms/millimetres sees two unit systems side by side.** → Accepted: silent conversion of weight and balance data is a worse failure than mixed units, and the alternative (forcing one system at entry) mismatches POH data the pilot is copying from. A later change can add an explicit, labeled display-unit preference.
- **[Trade-off] Storing the engine series as JSONB gives up per-sample querying and puts a multi-hundred-kilobyte document in a row.** → Accepted for the read pattern actually specified (one strip over the most recent flight), bounded by the import-time downsample cap and the file-size limit. The normalized table remains addable later without changing the display path.
- **[Risk] Free-text remarks and pilot-entered document references are rendered back into HTML.** → Mitigation: Nunjucks autoescaping is on and no fleet template uses `| safe` on pilot-supplied values; a test submits a remark containing markup and asserts it is escaped in the rendered output. Parameterized queries are already the data-foundation rule.
- **[Risk] The maintenance panel could be read as an airworthiness verdict, which is precisely the misreading an aviation-adjacent tool must not invite.** → Mitigation: a spec requirement and its test forbid any "airworthy"/"cleared to fly" assertion and require the pilot-entered caveat on every render of the panel.

## Migration Plan

Forward-only, in the order the tasks implement them; there are no down migrations, per the data-foundation convention. Each migration is independently applicable and leaves the application working, because the module registers its panels incrementally.

1. **`004_aircraft.sql`** — `aircraft` (identity columns, `opening_airframe_hours`/`opening_engine_hours`/`opening_tach_hours`/`opening_landings`, `retired_at`, standard columns and trigger, `pilot_id` FK, `UNIQUE (id, pilot_id)`, the normalized-registration unique index), then `ALTER TABLE pilots ADD COLUMN active_aircraft_id uuid REFERENCES aircraft(id) ON DELETE SET NULL`.
2. **`005_aircraft_documents_and_wb.sql`** — `aircraft_documents` (kind, reference, issued_on, expires_on) and the weight-and-balance columns plus `aircraft_load_stations` and `aircraft_cg_envelope_points`, all with the unit columns from decision 2.
3. **`006_flight_entries.sql`** — `flight_entries` with the `kind` discriminator, the check constraints from decision 1, the duration/counter columns from decision 2, and the two listing/aggregate indexes.
4. **`007_maintenance_items.sql`** — `maintenance_items` (description, due_on, due_at_hours, hours_basis, recurrence_months, recurrence_hours, reference) and `maintenance_completions` (completed_on, completed_at_hours, reference).
5. **`008_engine_data_files.sql`** — `engine_data_files` with the provenance columns and the `channels`/`series`/`ignored_columns` payload, one row per flight entry at most (`UNIQUE (flight_entry_id)`).
6. Seed additions (step 16 above) land with migration 006, since they need aircraft and flights to be meaningful.

**Rollback:** reverting the module registration in `src/modules/fleet/index.ts` to `registerPlaceholderScreen` restores the previous screen with the tables left in place and unread; the shell's active-aircraft control falls back to its "none selected" state, which is also its behavior for a pilot who has chosen nothing. No data migration is required to roll back, and no other module reads these tables in this change.

**Deployment order:** migrations before the application, as usual; the new configuration values all have defaults, so no environment change is required to deploy.

## Open Questions

- Should the engine-data import sit behind a configuration flag for the first release, given it is the only Tier 1 slice on this screen and the only one carrying a new dependency? Defaulting it off would let the rest ship while a real avionics export is tested against the format registry. Needs a call before the import tasks start, not before the change starts.
- Which engine-monitor exports must be recognized on day one? The format registry makes adding one cheap, but the generic header matcher's fallback behavior (accept anything with recognizable column names, or refuse unless a specific format is detected) depends on whether a real file is available to test against.
- Should recent-experience windows be configurable, or is 90 days the only one worth showing? The specs fix 90 days because that is the window pilots actually check; a configurable window is trivial to add if instrument recency (6 months) is wanted later.
- Does the airworthiness panel eventually need the document *file* attached, not just its dates? The `documents` module already owns storage and retrieval of PDFs; linking an `aircraft_documents` row to a `documents` row is the obvious future join and is deliberately not built here.
